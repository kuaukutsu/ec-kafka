## 1. Как читать ревью

### Модель серьёзности

| Уровень | Что означает | Пример из мира Go |
|---|---|---|
| **Critical** | Ломает архитектуру или корректность системы | handler ходит в БД мимо сервиса |
| **Major** | Серьёзно вредит поддержке, тестируемости или надёжности | God-object, потерянный контекст, зависший shutdown |
| **Minor** | Локальный недочёт качества | нейминг, лишние параметры |
| **Note** | Наблюдение, вопрос, риск без явного нарушения | осознанный компромисс, который стоит записать |

### Порядок проверки (почему именно такой)

1. Границы слоёв и пропуск слоёв.
2. Утечки доменной логики, God-objects.
3. Чистота домена.
4. Только потом идиомы Go и локальное качество.

Так делают, чтобы не «полировать» имена, пока в коде остаётся фундаментальная проблема.

## 2. Что в проекте сделано хорошо

Ревью — не только список недостатков. Эти решения стоит перенять в своих проектах.

### 2.1. Интерфейсы объявлены на стороне потребителя

```go
// internal/queue/producer.go — интерфейс живёт там, где он нужен
type QueueProducer interface {
    ProduceSync(ctx context.Context, msg Message) error
}
```

Пакет `queue` ничего не знает про `kgo`. Адаптер `pkg/kafka` подстраивается под интерфейс
(`var _ queue.QueueProducer = (*client)(nil)` проверяет это на этапе компиляции).
Благодаря этому транспорт можно заменить, а бизнес-код тестируется на фейках.

### 2.2. Цикл потребления отделён от клиента через `poller`

```go
// pkg/kafka/consume.go
type poller interface {
    PollFetches(ctx context.Context) kgo.Fetches
    CommitRecords(ctx context.Context, rs ...*kgo.Record) error
    AllowRebalance()
}
```

Интерфейс — минимальное подмножество `*kgo.Client`, нужное циклу. Поэтому сложная логика
остановки покрыта юнит-тестами с фейком, без брокера (`consume_test.go`, 532 строки).

### 2.3. Корректная логика graceful shutdown

- Остановка по сигналу — не ошибка: `consume` возвращает `nil`.
- Проверка `ctx.Err()` стоит **до** разбора fetch-ошибок: отменённый poll сам сообщает
  `context.Canceled` как fetch-ошибку.
- Коммит после остановки идёт на контексте без отмены (`context.WithoutCancel`) с таймаутом 5s.
- Запись, которую обработчик не успел обработать из-за остановки, не коммитится и приходит повторно (at-least-once).
- `defer p.AllowRebalance()` вызывается после коммита, поэтому ребаланс не блокируется навсегда.

### 2.4. `FailurePolicy` как шов под будущий DLQ

`LogAndSkip` — единственная политика, но решение «что делать с упавшей записью» уже вынесено
в интерфейс. Добавить DLQ позже можно без переписывания цикла.

### 2.5. Повторный сигнал убивает процесс

```go
go func() {
    <-ctx.Done()
    stop() // after the first signal, restore default behavior
}()
```

Если shutdown завис, второй `Ctrl+C` сработает штатно.

## 3. Major-находки

### M1. `closer.Close` может зависнуть навсегда

- **Location:** `internal/app/closer.go:97` (`lateWg.Wait()`), ветка таймаута на строках 78–93
- **Category:** idiomatic-go (конкурентность)
- **Owner:** engineer + test-writer

#### Что в коде

```go
select {
case err := <-done:
    ...
case <-iterCtx.Done():                     // timeout fired
    errs = append(errs, fmt.Errorf("closer: %s: timed out after %s", ...))
    lateWg.Add(1)
    go func(name string, ch <-chan error) { // watcher for the late result
        defer lateWg.Done()
        if err := <-ch; err != nil { ... }  // blocks until fn finally returns
    }(f.name, done)
}
...
lateWg.Wait() // waits for ALL late functions
```

#### Почему это проблема

Идея автора правильная: таймаут нужен, чтобы функции, не знающие про `ctx`, не вешали остановку.
Но в конце `Close` стоит `lateWg.Wait()`. Он ждёт все функции, которые уже «опоздали».
Если такая функция не завершится вообще, `Close` не вернётся никогда.

Таймаут 10s срабатывает только как **запись в ошибку**, а блокировку не снимает.

#### Почему это не теоретическая проблема

`cl.Close()` из `kgo` не принимает `context` и во время выхода из consumer group обращается
к брокеру. Это ровно тот класс функций, ради которых написан таймаут в closer. Сейчас в closer
регистрируются именно такие вызовы (`internal/app/queue.go:24` и `:47`).

#### Как воспроизвести

Зарегистрировать в closer функцию `func(ctx) error { select {} }` (вечный сон) и вызвать `Close`.
Ожидание: возврат за ~10s с ошибкой. Факт: зависание.

#### Направление исправления

Не ждать опоздавшие функции. Логирование их позднего завершения достаточно оставить фоновой
горутиной. Если нужна гарантия «все успели или нас убили», ограничить ожидание отдельным общим
дедлайном.

#### Чему учит

> **Таймаут, который не прерывает ожидание, — не таймаут.**
> Каждый раз, когда вы ограничиваете время операции, проверьте, нет ли *после* этого ограничения
> безусловного `Wait()`, `<-ch` или `wg.Wait()` на той же операции.

В Go «горутину нельзя убить». Поэтому у функции без `ctx` есть только два выхода: подождать её или
бросить. Если решили бросить, надо действительно бросить.

#### Какой тест нужно написать

`closer_test.go` сейчас отсутствует вовсе. Минимум:

- LIFO-порядок вызова;
- идемпотентность (второй `Close` возвращает тот же результат, функции не вызываются повторно);
- функция, которая ждёт дольше `closerIterationTimeout`: `Close` возвращается вовремя;
- агрегация нескольких ошибок через `errors.Join`.

Для теста таймаут лучше сделать полем структуры, а не константой, иначе тест будет идти 10 секунд.

### M2. Пустой `Key` превращается в непустой `[]byte`: все сообщения без ключа идут в одну партицию

- **Location:** `pkg/kafka/client.go:44` (`ProduceSync`); `internal/queue/message.go:18` (`GetKey`)
- **Category:** correctness
- **Owner:** engineer + test-writer

#### Что в коде

```go
record := &kgo.Record{
    Topic: msg.Topic,
    Key:   []byte(msg.Key), // msg.Key == "" gives an empty, but NOT nil, slice
    Value: []byte(msg.Value),
}
```

#### Почему это проблема

В Go `[]byte("")` — это пустой слайс, но **не `nil`**. Проверено:

```go
b := []byte("")
fmt.Println(b == nil, len(b)) // false 0
```

Партиционер `franz-go` различает эти два случая (`pkg/kgo/partitioner.go`, v1.22.2):

```go
func (p *stickyKeyTopicPartitioner) Partition(r *Record, n int) int {
    if r.Key != nil {
        return p.hasher(r.Key, n)          // key present: hash of the key
    }
    return p.stickyTopicPartitioner.Partition(r, n) // key == nil: sticky/spread
}
```

Пустой, но не `nil` ключ хешируется. У всех пустых ключей хеш одинаковый, значит все
такие сообщения попадают в **одну и ту же партицию**.

#### Что видит пользователь

Демо-продюсер (`cmd/producer/main.go:56`) не задаёт `Key`. Если сломанный код дойдёт до реального
сервиса, в топике из 3 партиций работает одна. Остальные два консьюмера группы простаивают.
Ошибок нет, сообщения доставляются, и проблема видна только в метриках нагрузки.

#### Направление исправления

В `ProduceSync` оставлять `Record.Key == nil`, когда `msg.Key == ""`. Лучше сделать это в одном
месте (`GetKey` в `Message`) и использовать его везде. Сейчас метод есть, но не вызывается
(см. m5), а конвертация продублирована.

#### Чему учит

> **Пустое значение и отсутствие значения — разные вещи.**
> При конвертации «строка ↔ `[]byte`» нулевое значение `""` по умолчанию превращается в
> «значение есть, оно пустое». Если нижележащая библиотека различает «нет ключа» и «пустой ключ»,
> это надо учитывать явно.

Хороший вопрос на ревью: *«а что делает библиотека с `nil` и с пустым значением — это одно и то же?»*

#### Какой тест нужно написать

Вынести сборку `kgo.Record` в чистую функцию и проверить: `Key: ""` даёт `record.Key == nil`,
`Key: "a"` даёт `[]byte("a")`. Тест не требует брокера.

### M3. Нет валидации `queue.seed`: клиент молча уходит на `127.0.0.1:9092`

- **Location:** `internal/config/config.go:27` (`Queue.Seed`); `internal/app/queue.go:12` (`MakeProducer`)
- **Category:** architecture (конфигурация)
- **Owner:** engineer + test-writer

#### Что в коде

Для консьюмера есть явная проверка:

```go
func (a *app) MakeConsumer(ctx context.Context, cfg *config.Config) (...) {
    if err := cfg.Queue.Consumer.Validate(); err != nil { // group and topic are required
        return nil, fmt.Errorf("consumer config: %w", err)
    }
```

Для `seed` проверки нет, и `MakeProducer` не проверяет вообще ничего.

#### Почему это проблема

`Brokers()` на пустой строке возвращает `nil`. Документация `kgo.SeedBrokers` прямо говорит,
что без вызова брокер по умолчанию — `127.0.0.1:9092`:

```go
// SeedBrokers sets the seed brokers for the client to use, overriding the
// default 127.0.0.1:9092.
```

Если переменная `KAFKA_SEED` не задана в окружении (опечатка в манифесте, забыли секрет),
приложение не упадёт с понятной ошибкой. Оно попробует подключиться к localhost. В Docker/K8s это
выглядит как «таймаут при пинге», и причина неочевидна.

Заметьте также: в `config.go` `Env` по умолчанию `production`, а допустимость значения не
проверяется. Опечатка `prodution` даст JSON/Info-логирование без единого предупреждения.

#### Направление исправления

Добавить `Queue.Validate()` (по аналогии с `Consumer.Validate()`) и вызывать его в обоих `Make*`.
Проверять и допустимое значение `Env`.

#### Чему учит

> **Fail fast: отсутствие обязательной настройки должно приводить к немедленной понятной ошибке,
> а не к «разумному значению по умолчанию» библиотеки.**

Дефолты библиотеки подходят для её примеров, а не для вашего окружения. Хорошее правило:
для каждой настройки, которая **определяет, куда пойдут данные**, дефолта быть не должно.

## 4. Minor-находки

Все эти пункты не ломают систему, но накапливаются. Для каждого указано, что видеть и как улучшить.

### m1. Неиспользуемые параметры и поля в `app`

- **Location:** `internal/app/app.go:16`
- `NewApp(ctx, log, cfg, name)`: `ctx` и `name` нигде не читаются. Поле `app.cfg` не читается, потому что `Make*` принимают `cfg` отдельным аргументом.
- **Урок:** лишний параметр — это ложное обещание в сигнатуре. Читающий думает, что `name` на что-то влияет. Определитесь: конфиг живёт в структуре **или** передаётся аргументом.

### m2. Экспортируемые конструкторы возвращают неэкспортируемые типы

- **Location:** `NewApp` → `*app`, `NewCloser` → `*closer`, `kafka.New` → `*client`
- Вызывающий код не может объявить переменную такого типа вне пакета, а `golint`/`revive` на это ругаются.
- **Урок:** принцип «accept interfaces, return structs» предполагает, что структура **экспортирована**. Если тип намеренно скрыт, возвращайте интерфейс.

### m3. Заикание в именах (stuttering)

- **Location:** `queue.QueueProducer`, `queue.QueueConsumer`; метод `client.Consumer`
- Снаружи читается как `queue.QueueProducer`. В Go принято `queue.Producer`-подобное имя без повтора пакета. Метод `client.Consumer` блокирует и крутит цикл, поэтому по смыслу это `Run`/`Consume`, а не существительное.
- **Урок:** имя пакета — часть имени. Читайте идентификатор целиком, как его увидит вызывающий.

### m4. Захардкоженный таймаут пинга

- **Location:** `pkg/kafka/client.go:29`
- `context.WithTimeout(ctx, 1*time.Second)` игнорирует `queue.timeout` из конфига (в `local.yaml` это `2s`, но применяется только к `DialTimeout`). Три брокера на медленной сети могут не успеть.
- **Урок:** настройка в конфиге, которая действует не везде, хуже, чем её отсутствие.

### m5. Неиспользуемые `Message.GetTopic/GetKey/GetValue`

- **Location:** `internal/queue/message.go:14`
- `grep` не находит ни одного вызова. В то же время `ProduceSync` дублирует конвертацию вручную (и именно там живёт баг M2).
- **Урок:** мёртвый код — это не только «лишние строки». Здесь он ещё и прячет единое место, где можно было бы исправить M2.

### m6. `config.New` паникует и регистрирует глобальный флаг

- **Location:** `internal/config/config.go:73`, `fetchConfigPath`
- `flag.StringVar` пишет в глобальный `flag.CommandLine`. Повторный вызов `New()` упадёт с паникой «flag redefined». Ошибки чтения конфига — тоже `panic`, а не `error`.
- Это объясняет покрытие 41.7%: путь через флаг в тестах недостижим.
- **Урок:** `panic` допустим в `main` (там некому обработать ошибку), но не в функции, которую вызывают из тестов и других мест. Библиотечный код возвращает `error`. Глобальное состояние (`flag`, `os.Args`) делает код непредсказуемым в тестах.

### m7. Дублирование шаблона запуска и расхождение в `Close`

- **Location:** `cmd/consumer/main.go:32`, `cmd/producer/main.go:33`
- Блок с сигналами и горутиной повторного `stop()` скопирован. Консьюмер вызывает `application.Close(ctx)`, продюсер `application.Close(context.WithoutCancel(ctx))`. Closer сам делает `WithoutCancel`, так что поведение одинаковое, но выглядит как разное намерение.
- **Урок:** расхождение между копиями — первый признак того, что общий код пора выделить. Читающий задаётся вопросом: «это разные требования или забыли поправить?».
